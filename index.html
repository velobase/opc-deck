不要让人类限制了 AI

一人公司的商业化底座实践

Jerry · Velobase

大家好，我是 Jerry，Velobase 创始人。今天15分钟，跟大家聊一个很具体的事情：做一个能赚钱的 AI SaaS，除了核心功能之外，到底还需要做哪些事。不讲大词，全是实操。

AI 写代码越来越强了，
但大部分一人公司，还是不赚钱。

常见误诊：「是不是 AI 写的业务还不够复杂？」

过去一年，大家感受很深：Cursor、Claude 越来越强，一个周末就能写出一个 MVP。但真正赚到钱的独立开发者并没有变多。大部分人的第一反应是——是不是核心功能还不够好？但我看了很多死掉的项目，发现不是这么回事。

我们用 AI 做出了「功能」

但没做成「生意」

痛点不在 AI 的智商，
在于我们不知道一个能收钱的产品长什么样。

核心问题是：我们有了执行力（AI），但缺少认知。你让 AI 写个聊天界面一分钟就好了，但一个能收钱的 SaaS，它需要支付、需要对账、需要反滥用、需要广告归因、需要用户运营。大部分纯技术背景的人，根本不知道要做这些东西。你都不知道要让 AI 写什么，AI 再聪明也帮不了你。

AI 可以一句话搞定：

登录页 CRUD 大模型对话 Landing Page

但 AI 没法自己规划这些：

支付状态机 + 掉单补偿 广告归因回传 反滥用策略 定价 A/B 实验 Chargeback 举证 用户 LTV 分群

不是写不出来，是大部分人不知道要写这些。

具体来说。让 AI 写个登录页、写个 CRUD、接个大模型，这些一分钟就搞定了。但支付掉单补偿、广告服务端回传、Gmail 别名防刷、定价 A/B 实验、Chargeback 举证流程、用户 LTV 分群分析——这些全是你必须做但可能从来没想过的事。不是 AI 写不出代码，是你压根不知道要提这个需求。

我们把赚到钱的这套框架开源了。
它不只是代码——通过结构和文档告诉你：
一个商业化 SaaS 应该长什么样。

有了图纸，AI 才能精准施工。

所以我们做了 Velobase Harness，一个开源的全栈商业化框架。它最大的价值不是那几万行代码本身，而是通过目录结构和文档，告诉你——你要做一个能赚钱的 SaaS，你需要准备哪些基础能力。说白了它是我们踩了无数坑之后，沉淀出来的一套业务最佳实践。你有了这张图纸，再让 AI 去写代码，效率完全不一样。

Know-how #1

Stripe Webhook 会丢。
用户付了钱，你不知道。

网络抖动、服务重启、部署间隙——Webhook 没收到。
订单卡在 PENDING，用户付了钱没权益。

→ 每分钟扫描 PENDING 订单，主动查 Stripe 真实状态。
→ 每小时全量对账。不论 Webhook 丢不丢，都不漏单。

第一个知识点：支付掉单。Stripe 通过 Webhook 通知你付款成功，但 Webhook 本质上是一个 HTTP POST，网络会抖动、你的服务可能刚好在重启。Webhook 丢了，用户付了钱你不知道。Harness 的做法是后台每分钟扫描所有超时 PENDING 订单，主动去 Stripe API 查真实状态；每小时还有一次全量对账。这是我们从 scripts/run-payment-reconciliation.ts 和 scripts/detailed-billing-reconcile.ts 中沉淀出来的。

Know-how #2

同一个人，无限个邮箱。

john.doe@gmail.com

johndoe@gmail.com

j.o.h.n.d.o.e@gmail.com

johndoe+free1@gmail.com

↑ Gmail 忽略点和加号后缀，全是同一个人。

→ 注册时自动规整化：去点、去 + 后缀、统一比对。

第二个：Gmail 别名滥用。Gmail 有个特性：用户名里的点会被忽略，加号后面的内容也被忽略。一个人可以用 johndoe、j.o.h.n.d.o.e、johndoe+1 注册无数个账号薅你的免费积分。我们在 scripts/backfill-canonical-email.ts 里做了全量修复，在框架里注册环节自动做邮箱规整化。

Know-how #3

前端追踪被 AdBlock 吃掉 30%。
你的广告数据全是假的。

前端 gtag 被拦截 → 转化事件发不出去 → ROAS 严重失真。

→ 三层链路：落地页采集 gclid → 注册时绑定用户 → 付费后服务端离线回传 Google Ads API。
→ 服务端回传不经过浏览器，AdBlock 拦不住。

第三个：广告归因。你投 Google Ads，前端装 gtag 追踪转化。但 30%+ 用户有 AdBlock，gtag 请求直接被屏蔽。你的 ROAS 数据是假的。Harness 的三层归因：前端采集 gclid 存 Cookie → 注册时写入 User 表 → 付费后通过 BullMQ 队列从服务端批量上传 Google Ads API。这是 scripts/backfill-google-ads-conversions.ts 和 scripts/analyze-ad-efficiency-trend.ts 的实战沉淀。

Know-how #4

反滥用不能让正常用户等。

同步检测所有风险（IP / 设备指纹 / 邮箱关联）需要 2-3 秒。
99% 正常用户被 1% 坏人拖慢。

→ 「先发后收」：注册时只做轻量检测，立即放行。
→ 异步检测同 IP 多账号、设备指纹。确认滥用后回收积分。

第四个：先发后收。反滥用必须做，但不能阻塞正常用户。同步检查 IP、设备指纹、邮箱关联性需要好几秒。Harness 的策略是注册时只查一次性邮箱黑名单（毫秒级），立即放行发积分。后台异步跑 scripts/analyze-abuse.ts 的逻辑：查同 IP 多账号、设备指纹关联。确认是滥用后自动回收积分。正常用户零感知。

Know-how #5

用户付了钱，用完了，再申请退款。
你有 7 天举证窗口。

Stripe Dispute：银行冻结资金，你必须提交证据证明服务已交付。
证据不足 → 钱退给用户 + 你额外被罚 $15。

→ 自动导出：支付记录 + 服务使用记录 + 登录 IP + 时间线。
→ 打包提交 Stripe Evidence API。

第五个：Chargeback 举证。用户在 Stripe 上发起争议（Dispute），银行会直接冻结这笔钱，你有 7 天时间提交证据证明你确实提供了服务。如果你没有自动化的证据收集流程，7 天根本来不及。我们在 scripts/export-evidence-for-stripe.ts 里实现了自动证据导出：拉出该用户的所有支付记录、服务使用记录（什么时间生成了什么内容）、登录 IP，格式化后提交。Harness 把这个流程标准化了。

Know-how #6

定价不能拍脑袋。
$4.99 还是 $9.99？跑实验。

50% 用户看到价格 A，50% 看到价格 B。
追踪转化率和 ARPU，用数据决策。

→ PostHog Feature Flag + Experiment API 自动创建。
→ 框架层集成，改配置即跑实验，不动业务代码。

第六个：定价实验。$4.99 好还是 $9.99 好？不能猜。Harness 集成了 PostHog 的 Feature Flag 和 Experiment API，我们在 scripts/posthog/create-pricing-experiment.ts 里可以一键创建定价 A/B 实验。50% 用户看到价格 A，50% 看到价格 B，追踪实际付费转化率。用数据决策，不靠直觉。框架层面集成意味着你改个配置就能跑实验，不需要动业务代码。

刚才讲了6个具体的坑。但运营一个 AI SaaS，日常实际要做的远不止这些。我们的 scripts 目录有 200 多个脚本，覆盖财务对账、广告 ROI 分析、反滥用调查、定价实验、客服回复、营销活动。这些全是代码之外的事情。一个人做这些，必须有系统化的工具支撑，否则精力会被碎片化运营彻底吃掉。

配置即启动，代码只写业务

# 填了就开，不需要改代码
STRIPE_SECRET_KEY=sk_live_...
GOOGLE_ADS_CUSTOMER_ID=123-456-7890
POSTHOG_KEY=phc_...
ENABLE_ANTI_ABUSE=true

# 一套代码，三个进程
SERVICE_MODE=all # 本地全合一
SERVICE_MODE=web,api,worker # 生产分开跑

可插拔模块 + 事件总线。业务成长到哪一步，就启用哪个模块。

使用方式很简单。环境变量驱动——填了 Stripe key，支付模块就开了；填了 Google Ads ID，归因就自动跑；PostHog key 填上，埋点和实验就有了。核心设计是可插拔模块加事件总线，所有模块通过事件解耦。比如 payment:succeeded 这个事件触发后，会自动通知广告归因模块回传转化、通知飞书发运营消息、通知 PostHog 记录付费事件。你的业务成长到哪一步，就启用哪个模块，不需要重构。
